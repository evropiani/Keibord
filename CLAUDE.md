# Keibord — notes for coding agents

- Spec: `docs/ARCHITECTURE.md`. Core logic lives in the `Core/` Swift package (Foundation only, testable on Linux): `swift test --package-path Core`.
- iOS code: `Shared/` (compiled into app + keyboard), `Keyboard/Sources` (UIKit extension, keep memory low, no SwiftUI), `App/Sources` (SwiftUI).
- There is no Mac: the Xcode project is generated by XcodeGen on GitHub Actions; iOS code is only compiled there. Keep iOS APIs conservative (iOS 17 SDK).
- Keyboard height (iOS 26/27): keep `inputView.allowsSelfSizing = true` plus the 999-priority height constraints on the view and the sizer, set once in viewDidLoad. Without `allowsSelfSizing` iOS gave 241/224 pt in every app whatever else was tried (required constraint, preferredContentSize, nudges; 1.0.14–1.0.17); restoring it fixed the height everywhere (1.0.18). Never change the height while the keyboard is on screen (no re-request in viewDidAppear, one height for every page, field and mode, emoji search included); only a height iOS ignored is requested again. Never read `textDocumentProxy.documentIdentifier` before viewWillAppear (crashed 1.0.14).
- Glass band (iOS 26/27): iOS draws a 17 pt glass band above third-party keyboards, host-side, and adds or drops it by itself: always there in Spotlight and the App Library; in apps missing at first, added after an app switch or Apple's own keyboard (password fields), dropped again by Apple's Emoji keyboard (Apple developer forums thread 843093, FB24460699, any third-party keyboard). The extension's view, window, safe area and backgrounds are identical either way, so it can be neither detected nor compensated, and no single word position is centred in both cases (mocked up from the 1.0.20 screenshots). `SuggestionBarView.textOffset` (2.5 pt below the bar's middle, 1.0.21) splits the difference, leaning towards apps without the band; 1.0.8–1.0.20 placed the words for the band, and in apps they sat against the edge. Do not chase the band with height or lifecycle changes: 1.0.20 wrongly blamed height changes on screen.
- Language keyboards (1.0.22): one keyboard extension per language (`KeibordKeyboard` = Keibord Deutsch, keeping the first keyboard's bundle id so iOS keeps it enabled with Full Access; `KeibordKeyboardEN/SQ/IT`), no language key. Their code, dictionaries and emoji live once in `KeibordKeyboardKit.framework` (Keyboard/Sources + Shared + Resources), embedded in the app and loaded by each extension via `@executable_path/../../Frameworks`; each extension has only `Keyboard/Entry` and an Info.plist naming `KeibordKeyboardKit.KeyboardViewController` and `KeibordKeyboardLanguage`. Load resources with `Bundle(for:)`, never `Bundle.main` (that is the extension). The CI package step signs and checks every bundle.
- Look: the default colours are the iOS 26/27 keyboard measured from screenshots (all keys #FFFFFF / #454545, function keys like letters, no shadows, letters 24.5 pt, words 18 pt, space bar with "DE EN" only). Settings version 2 turned old default shadows off.
- Rules: tolerant Codable decoding for persisted models; Core API used by the app/keyboard must be `public`; no networking code; never hard-code the app group (use `AppGroup`).
- Distribution: the developer name shown in store listings and sources is **evropiani** (not a personal name). The owner maintains their own third-party store source and updates it manually with a script: releases update no store source or gist (the gist automation was removed); `distribution/keibord-source.json` is only a reference copy of the AltStore format and is not synced after releases.
- Releases: when a change is done and CI is green, publish it right away without asking (bump `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` in project.yml, write docs/RELEASE_NOTES.md, then run the Build workflow with `release_tag` vX.Y.Z).
